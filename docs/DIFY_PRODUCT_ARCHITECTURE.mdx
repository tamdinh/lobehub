# Dify Product Architecture

## 1. Purpose

Build the consumer AI SaaS product on top of the **Dify codebase as the AI platform core**, while using a **LobeHub-like product UX**.

Core decision:

- **Dify = AI platform / execution engine**
- **Product Layer = consumer SaaS product / UX / monetization**
- **Dify Adapter = integration boundary**

Do not merge Dify and LobeHub into one codebase. Use LobeHub as an architectural and UX reference.

## 3. Architectural Principles

### P1 — One Source of Truth

Do not duplicate Dify domain objects in Product DB.

**Dify remains authoritative for:**

- Apps
- Agents
- Workflows
- Workflow versions
- Knowledge bases
- Documents
- Segments
- Providers
- Credentials
- Plugins
- Tools
- Executions
- Runtime state
- Dify workspaces
- Dify membership/RBAC

**Product DB remains authoritative for:**

- Product users
- Plans
- Subscriptions
- Entitlements
- Billing
- Usage/quota
- Product catalog
- Analytics
- Support
- Moderation
- Notifications

### P2 — Product Code Must Not Depend Directly on Dify Internals

**Bad:**

```text
Product UI -> Dify SQLAlchemy models
Product UI -> Dify internal services
```

**Preferred:**

```text
Product UI
   -> Product API
      -> Dify Adapter
         -> Dify API / controlled integration
```

### P3 — Keep Dify Replaceable

Product concepts should not expose Dify implementation details everywhere.

For example:

- `ProductAgent`
- `ProductWorkflow`
- `ProductKnowledgeBase`
- `ProductTool`
- `ProductProvider`

map internally to Dify objects.

### P4 — Prefer WRAP over FORK

**Priority order:**

1. Product Layer
2. Existing Dify APIs
3. Dify plugin/extension
4. Adapter integration
5. Minimal Dify fork
6. Replacement only when unavoidable

### P5 — Product UX is Independent from Dify Console

**Initial:**

- `app.example.com` → Product UX
- `studio.example.com` → Dify Console
- `admin.example.com` → Product Admin

Long-term, Dify Console is primarily an advanced/internal configuration surface.

## 10. Authentication

Dify already provides:

- Accounts
- Sessions
- Workspaces
- Membership
- Roles
- Invitations
- Permissions

Therefore do not maintain Clerk as a second identity system unless a concrete requirement exists.

**Mapping:**

```text
Product User
    |
    +-- dify_account_id

Product Workspace
    |
    +-- dify_tenant_id
```

Do not inject a Clerk session into Dify Console.

For the initial architecture:

```text
Public Product
    |
    v
Product API
    |
    v
Dify API
```

Dify Console can remain separately authenticated during migration.

## 11. Dify API Surfaces

Dify has two important API concepts:

### Public Service API (`/v1/...`)

Used for published application execution:

- Chat
- Completion
- Workflow execution
- Published app execution

*Do not use this as the product identity API.*

### Console API (`/console/api/...`)

Used for:

- Applications
- Workflows
- Datasets
- Providers
- Plugins
- Members
- Configuration
- Workspace management

The Product Adapter should encapsulate these details.

## 12. Billing and Entitlements

Billing is the Product Layer's responsibility.

**Execution flow:**

```text
POST /api/agents/:id/run

1. Authenticate user
2. Resolve workspace
3. Verify subscription
4. Verify entitlement
5. Verify quota
6. Invoke Dify
7. Stream response
8. Record product usage
```

- Dify executes the request.
- Product decides whether the user is entitled to execute it.

## 21. Dify Module Disposition

### KEEP

Keep essentially intact:

- Agent
- Workflow
- Knowledge
- Dataset
- Document
- RAG
- Model Provider
- Tool
- Plugin
- Runtime
- Execution
- Workspace
- RBAC
- Credential
- Integration
- Logging

### WRAP

Wrap through Product Adapter:

- App API
- Agent API
- Workflow API
- Knowledge API
- Provider API
- Plugin API
- Tool API
- Execution API
- Workspace API

### FORK

Fork only when Product Layer, adapter, plugin, or configuration cannot satisfy the requirement.

Potential areas:

- Authentication integration
- Product-specific API endpoints
- Specific runtime hooks
- Required platform integration

*Document every fork.*

### REPLACE

Replace only where Dify fundamentally conflicts with product requirements.

Typical replacements belong in Product Layer:

- Consumer UI
- Billing UI
- Product analytics
- Product catalog
- Mobile UI
- Product admin

## 25. Error Mapping

Translate Dify errors into stable Product errors.

| Dify Error              | Product Error            |
| :---------------------- | :----------------------- |
| `ProviderQuotaExceeded` | `AI_USAGE_LIMIT_REACHED` |
| `AppNotFound`           | `AGENT_NOT_FOUND`        |
| `PermissionDenied`      | `ACCESS_DENIED`          |

Never expose raw Dify internal exceptions to consumers.

## 28. Upstream Strategy

Keep Dify close to upstream:

```text
upstream/dify
       |
       +---- product integration
       |
       +---- minimal patches
```

Classify modifications as:

- `PRODUCT`
- `UPSTREAM`
- `INTEGRATION`
- `LOCAL-INFRA`

**Goal:**

```text
Dify update
   |
   v
merge/rebase
   |
   v
minimal conflict resolution
   |
   v
product tests
```

Avoid a heavily divergent Dify fork.

## 29. Upgrade Policy

Before each Dify upgrade:

1. Read release notes.
2. Review database migrations.
3. Review API changes.
4. Review Plugin Daemon compatibility.
5. Review Agent runtime changes.
6. Run adapter contract tests.
7. Run Product integration tests.
8. Run critical workflow tests.
9. Run web/mobile smoke tests.
10. Deploy staging.
11. Observe before production rollout.

Maintain `DIFY_VERSION` in product configuration.

## 31. Migration Plan

### Phase 0 — Product Concepts

Define core models:

- User, Workspace, Agent, Conversation, Workflow, Knowledge, Tool
- Subscription, Plan, Entitlement, Usage, ExploreItem

*(Do not expose Dify classes to UI code.)*

### Phase 1 — Adapter

Create `packages/dify-adapter` and implement:

- accounts, workspaces, apps, agents, workflows, knowledge

### Phase 2 — Product API

Move frontend Dify communication behind `/api/*`.

### Phase 3 — Authentication

Establish mappings:

- `Product User -> Dify Account`
- `Product Workspace -> Dify Tenant`

### Phase 4 — Billing

Implement:

- Plan, Subscription, Entitlement, Usage, and entitlement middleware.

### Phase 5 — Explore

Implement:

- Catalog, Featured, Categories, Search, "Use this Agent".

### Phase 6 — Consumer Chat

Build:

- Home, Agents, Chat, Explore, Activity, Profile using Dify execution.

### Phase 7 — Knowledge

Expose simplified knowledge UX.

### Phase 8 — Advanced Workflow

Initially expose Dify workflow authoring at `studio.example.com`.

### Phase 9 — Mobile

Build mobile against Product API.

### Phase 10 — Product Admin

Implement:

- Users, Subscriptions, Plans, Entitlements, Catalog, Analytics, Support, Moderation.

## 33. Things to Avoid

- **Do not create:** `Dify Agent Runtime` + `Custom Agent Runtime` unless required.
- **Do not create:** `Dify Knowledge` + `Second RAG system` for the same domain.
- **Do not duplicate:** `Product workflow_json` + `Dify workflow graph`.
- **Do not store:** Provider secrets in Product DB.
- **Do not make:** Product UI depend on Dify internals.
- **Do not use:** Dify iframe as the permanent consumer UX.

## 34. Security Model

**Product Layer enforces:**

- Authentication
- Authorization
- Subscription
- Entitlement
- Quota
- Tenant isolation

**Dify enforces:**

- Workspace authorization
- Resource permissions
- Provider credentials
- Tool/plugin permissions
- Execution permissions

Both layers are security boundaries. Never assume: `Product permission == Dify permission`.

- **Dify** provides the **AI PLATFORM**.
- The **Product Adapter** keeps them **DECOUPLED**.

## 39. Definition of Done

The architecture is established when:

- [ ] Product UI does not call Dify APIs directly.
- [ ] Product API owns consumer-facing contracts.
- [ ] Dify Adapter is the only Product Layer integration boundary.
- [ ] Product DB contains no duplicated Dify workflow/knowledge/provider state.
- [ ] Product user maps to Dify account.
- [ ] Product workspace maps to Dify tenant.
- [ ] Subscription and entitlement checks happen before AI execution.
- [ ] Agent execution works through Dify.
- [ ] Workflow execution works through Dify.
- [ ] Knowledge works through Dify.
- [ ] Tools/MCP work through Dify where supported.
- [ ] Explore entries reference Dify Apps rather than cloned definitions.
- [ ] "Use this Agent" uses Dify application copy/import capability.
- [ ] Product Admin is independent from Dify Console.
- [ ] Mobile uses Product API.
- [ ] Dify modifications are minimal and documented.
- [ ] Adapter contract tests pass.
- [ ] Dify upgrades can be tested without rewriting Product UX.
